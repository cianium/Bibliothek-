# گزارش بررسی و اصلاح German Library — 7.1.1

تاریخ: 2026-10-08 · مبنا: فایل German Library V7.1 ارسالی کاربر.

## نتیجه

معماری فعلی برای کتابخانهٔ گزیده و راهنمای یادگیری مناسب است و نیاز به بازنویسی یا React ندارد. این نسخه اصلاح‌شده برای اتصال به محیط آزمایشی آماده است؛ «منتشرشده» یا «تأییدشده روی دیتابیس واقعی» نیست. تنظیمات Supabase در فایل ورودی خالی بودند. هیچ سرویس، حساب، دیتابیس یا دامنه‌ای در این کار ایجاد یا تغییر نکرده است.

مدل داده تغییر ناسازگار ندارد. collection همچنان level یا special است. منابع مرتبط از طریق courseId به بسته متصل‌اند. coreCourseId کتاب اصلی سطح را تعیین می‌کند. مقدار داخلی extra با برچسب «اختیاری» نمایش داده می‌شود. وضعیت‌ها draft / published / archived باقی مانده‌اند. فایل‌ها در bucket خصوصی resource-files قرار می‌گیرند؛ انتشار منبع با انتشار خود bucket یکسان نیست.

مسیر کاربر: خانه ← انتخاب سطح ← مسیر پیشنهادی ← بستهٔ کتاب یا تمرین مهارت ← جزئیات/دسترسی منبع. ورود فقط برای مدیریت است؛ LMS، امتیاز یا پیشرفت ساختگی اضافه نشده است.

## پوشش واقعی محتوا

| سطح | کتاب اصلی | تعداد منابع سطح |
|---|---|---:|
| A1 | Starten wir! A1 | ۸ |
| A2 | Starten wir! A2 | ۸ |
| B1 | ندارد | ۵ |
| B2 | ندارد | ۵ |
| C1 | ندارد | ۴ |
| C2 | ندارد | ۳ |

دو منبع دیگر متعلق به دو بستهٔ ویژهٔ Grammatik aktiv هستند. هیچ رکوردی در این کار به فهرست اضافه یا حذف نشده؛ URL، provider، pricing و تاریخ بررسی منابع نیز بازنویسی نشده‌اند.

کمبود مهم محصول، تعداد امکانات نیست؛ پوشش هدایت و محتواست:

- B1 تا C2 کتاب اصلی ندارند. پیش از وعدهٔ «مسیر کامل»، برای هر سطح یک انتخاب مستدل و دارای مسیر دسترسی مشخص لازم است.
- هیچ منبعی با مهارت اصلی Lesen، Schreiben، Sprechen یا Aussprache ثبت نشده است. بعضی توضیحات به چند مهارت اشاره دارند، اما فیلتر فعلی تک‌مهارتی است. برچسب‌گذاری یا افزودن منابع باید با بررسی محتوای واقعی انجام شود.
- نوع Transcript در مدل پشتیبانی می‌شود ولی رکورد مستقل ندارد. صرف وجود این نوع نباید به ساخت مرحله یا فایل فرضی منجر شود.
- صفحات عمومی چندسطحی ناشران باید از نظر جلد دقیق و فایل واقعی بررسی شوند. valid URL به معنی فایل مستقیم، دسترسی رایگان یا مجوز بازنشر نیست.
- همهٔ رکوردها در مبنا linkStatus=ok و verifiedAt=2026-10-07 داشتند؛ این گزارش صحت زندهٔ همهٔ مقصدها را دوباره تأیید نکرده است.

## آزمون‌های انجام‌شده

- npm run qa: بدون خطای ساختاری و داده؛ آزمون Sync با client شبیه‌سازی‌شده.
- Regressionها: آرشیو فرزند پیش از والد، بازیابی آفلاین، حفظ تغییر remote روی ردیف دست‌نخورده، ویرایش حین fetch و write، جداسازی حساب‌ها، مسیر داده‌محور، parent visibility و کش Cloud.
- آزمون مرورگر Chromium headless: ۱۴ صفحه/مسیر در عرض‌های ۳۲۰، ۳۹۰، ۷۶۸ و ۱۴۴۰؛ مجموع ۵۶ بررسی صفحه/عرض، بدون horizontal overflow یا خطای JavaScript/CSP.
- مسیرهای تعاملی: جست‌وجو، صفر نتیجه، reset فیلتر، برچسب فرم‌ها، Tab/Shift+Tab داخل modal، ساخت و ویرایش منبع، حفظ ID واردشده و انتقال Core Book.
- بررسی تصاویر واقعی خانهٔ دسکتاپ، سطح A2 موبایل و modal ادمین. تصاویر در docs/screenshots قرار دارند.
- build و verify:dist با URL و کلید آزمایشی غیرواقعی پاس شدند. این آزمون، اتصال به Supabase را اثبات نمی‌کند. خروجی dist آزمایشی در ZIP تحویلی نیست.

آزمون مرورگر CDN/SDK را عمداً جایگزین کرده تا UI محلی مستقل بررسی شود؛ ورود واقعی، RLS، upload واقعی، signed URL، expiry و رفتار موبایل واقعی هنوز نیاز به آزمون روی deployment دارند. تست کامل WCAG و تست Safari ادعا نشده است.

## محدودیت‌های باقی‌مانده و ترتیب اقدام

### پیش از انتشار عمومی

1. پروژهٔ اختصاصی Supabase و مقصد hosting را مشخص کن؛ URL و publishable key را در environment مقصد قرار بده. secret/service_role لازم نیست.
2. schema را روی پروژهٔ آزمایشی اعمال کن؛ seed فقط برای دیتابیس اولیه است، نه بازنویسی محتوای موجود. یک حساب مدیریت بساز و نقش را از محیط امن تنظیم کن.
3. post-deploy-check.sql و Advisors را اجرا کن. anonymous/learner باید نتوانند تغییر ایجاد کنند؛ فقط فایل متصل به Published باید قابل دسترسی عمومی باشد. SQL موجود در این کار روی سرور واقعی اجرا نشده است.
4. با environment واقعی build بگیر، staging را باز کن و ورود، خروج، نقش‌ها، upload، آرشیو، قطع اتصال و فایل خصوصی را آزمایش کن.
5. لینک‌های نهایی و محتوای منتشرشده را بررسی کن؛ روی Android Chrome و iPhone Safari واقعی هم تست کن.
6. همان build آزموده‌شده را منتشر کن؛ backup داده، مسئول بررسی لینک‌ها و روش rollback مشخص باشد.

### پیش از مدیریت هم‌زمان توسط چند نفر

Sync فعلی روی ردیف‌های تغییرکرده upsert انجام می‌دهد و transaction سراسری یا optimistic concurrency سمت دیتابیس ندارد. تغییر هم‌زمان یک ردیف توسط دو ادمین می‌تواند last-write-wins شود؛ خرابی میان چند درخواست هم ممکن است وضعیت میانی بسازد. راه‌حل مرحلهٔ بعد، API/RPC تراکنشی با revision/updated_at و تشخیص conflict است؛ نیازمند طراحی و تست migration روی دیتابیس واقعی، نه تغییر عجولانهٔ RLS.

خواندن داده در Backend هنوز صفحه‌بندی کامل ندارد؛ با عبور از سقف پاسخ API ممکن است بخشی از فهرست دیده نشود. برای فهرست فعلی ۳۵‌تایی مانع نیست؛ پیش از رشد به سقف تنظیم‌شدهٔ API، pagination باید اضافه و آزموده شود.

### ارتقا از نسخه‌های قبلی

pending قدیمی V7.1 فاقد مالک بوده و خودکار به حساب فعلی نسبت داده نمی‌شود. پیش از جایگزینی نسخه، تغییرات unsynced نسخهٔ قبلی را Sync یا JSON Export کن. Import در Cloud ادغامی است؛ نبودن یک ردیف در JSON به معنی حذف آن از سرور نیست. برای حذف از نمایش از Archive استفاده کن.

schema شامل کد سازگاری قدیمی است، اما ترتیب constraintها نسبت به تبدیل فیلدهای legacy می‌تواند روی دادهٔ ناسازگار v6 شکست بخورد؛ آن را migration عمومیِ تست‌شده برای هر دیتابیس قدیمی فرض نکن. برای نسخهٔ مرجع فعلی، schema و دادهٔ موجود باید ابتدا در staging بررسی شوند.

## پیشنهاد مرحلهٔ بعد

اول اتصال واقعی و آزمون انتشار؛ سپس تکمیل کم‌تعداد منابع و کتاب اصلی سطح‌های ناقص. بعد از آن مدیریت conflict برای تیم محتوا و بررسی دوره‌ای لینک‌ها. افزودن پروفایل پیچیده، XP، streak یا موتور درس در این مرحله مسئلهٔ اصلی کتابخانه را حل نمی‌کند.
